## Persistent notification behavior and contracts

The owning notification model adds Notifications (xmin head), append-only NotificationEvents, per-actor/vessel NotificationPreferences and immutable NotificationReceipts. Tenant/vessel/source-plan-revision composite FKs, unique source-trigger identity, append-only/no-truncate history guards and immutable routing/source columns accompany the [source-authored migration](../../backend/Poseidon.Persistence/Migrations/20261104200000_NotificationFoundation.cs) and snapshot additions. Actual scaffold/designer/parity/application have not run and remain mandatory at the PR gate.

Trusted server `Notifications.Rules` supplies exact tenant/vessel, unique key, version/source reference, Due or ReviewRequired trigger state, severity and optional bounded escalation timer/role. Empty, ambiguous or invalid routing remains Unavailable. Configuration is declared technical routing, not verified evidence, maritime authority or an approved legal catalog. The source comes from actual current maintenance evaluation and eligible server-provisioned owner roles; client severity, recipient, actor and mandatory inputs cannot populate it. Critical always implies a mandatory in-app route. Preference can mute advisory visibility only; mandatory/Critical entries always survive that filter.

Refresh creates one source-trigger header and Raised event, escalates an open unacknowledged entry once when its recorded timer becomes due and a real eligible escalation role remains, and records SourceChanged when its pinned current basis changes. No text/date/recipient is silently overwritten in the original source record. Source identity includes deterministic calculation (state/reason/date/meter/algorithm), exact selected observation ID/time/assessment, asset revision, job and owner context; it excludes current/read/elapsed clocks. Dedupe includes this `SourceContextHash` as well as source revision and rule digest. The existing observation adapter pins immutable ObservationId: appending another still-Due reading does not silently switch the selected plan reading. Revocation/current assessment changes can retire old basis while the plan revision stays unchanged. Prior rows and lifecycle events remain immutable history. A retired identical basis is not automatically reopened; explicit source/policy evolution is required, and a general recurring-episode policy remains a later source decision.

Source refresh currently runs through an explicit authorized manager command. No background host schedule, polling worker or outbound delivery provider is installed. No delivered/read/external-receipt state is fabricated. This is a usable persistent InAppOnly source slice, not complete product-wide automated deadline delivery. New owning source adapters, approved routing/escalation catalogs and operational scheduler rollout remain open. Refresh bounds notice materialization at 2001 and rejects over 2000; the existing maintenance reader is still materialized before its 500-source guard, an explicit remaining bounded-reader improvement.

All API paths below begin `/api/v1/notification-escalation` and require DirectoryRead plus actual selected vessel scope. Read additionally requires trusted role context and `notification.read`, `maintenance.read`, `equipment.read`. Rows are limited to current recipient/escalation role or explicit scoped `notification.manage`; an actual Escalated event retains escalation-recipient visibility after acknowledgement for exact retry recovery. Manage also requires the ordinary vessel edit grant. No tenant-wide directory/admin capability alone grants notification management.

## Health observation semantics

`GET /api/v1/system-health?vesselId=UUID` requires explicit server `system.health.read`, audit.read, tenant-wide read/manage and actual vessel visibility. Navigation key `system-health` is emitted only under that server boundary. Notification utility navigation is independently emitted only under its owning read boundary. Neither expands the closed business lens catalog.

API request/error/average latency, audit success/failure/average latency and freshness observations have scope TenantProcessSinceStart. Tenant attribution is captured from trusted server membership after authorization, never from headers or exported metric labels. Anonymous/unattributed observations are excluded from these tenant snapshots; existing low-cardinality process metric instruments remain unchanged. No sample means state Unavailable with null numbers. A measured zero is returned only after actual observations. Cache capacity is bounded at 4096 tenant buckets and exhaustion remains Unavailable. These are neither durable lifetime totals nor a global cross-tenant dashboard.

Sync reports actual selected-vessel server committed outcomes and unresolved retained conflicts across crew/tug; a committed child resolution removes its parent from unresolved count without rewriting history. Client-only/disconnected queue backlog is null, never inferred as zero. File/scanner state is ConfiguredUnprobed or Unavailable and does not execute a provider/scanner probe or claim health from configuration. The endpoint performs current-scope checks before and after its mandatory read audit; failed audit persistence exposes no prepared metrics. This is a final response fence, not serializable revocation across socket emission.
