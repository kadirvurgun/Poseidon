1. API Tasarım Kararı

## paragraph:6

POSEIDON API'leri ekran-merkezli CRUD olarak tasarlanmayacaktır. 196 ekran kullanıcı projection'larıdır; canonical write/read sözleşmeleri domain aggregate ve command/query sınırlarında tanımlanır. Prototipte görülen /api/v1/<screen-id> yolları geliştirme sırasında UI Projection/Facade katmanına dönüştürülebilir.

## paragraph:7

Canonical resources: vessel, person/crew, operation, tug job, asset/PMS, safety event, certificate/survey/finding, document, evidence, regulatory rule.

## paragraph:8

Commands idempotent; kritik state transition'lar action/command olarak explicit.

## paragraph:9

Every request carries tenant/context authorization; client-supplied tenant alone is not trusted.

## paragraph:10

ETag/version optimistic concurrency for mutable aggregates.

## paragraph:11

Correlation ID end-to-end: API → outbox → integration → notification → audit.

## paragraph:12

Evidence upload is metadata-first + presigned/object-storage pattern; hashes/provenance server-side verified.

## paragraph:13

Offline commands replayable; material safety/legal conflicts never silent last-write-wins.

11. Security & Authorization

## paragraph:288

RBAC + object scope: tenant/company/vessel/tug/role; ABAC can add assignment/state restrictions.

## paragraph:289

Master/Tug Master onboard decisions require role + current vessel assignment, not only global role.

## paragraph:290

DPA fleet visibility and escalation rights separate from vessel operational approval.

## paragraph:291

Protected reporting identity is restricted to designated reviewers.

## paragraph:292

Regulatory rule publish uses separation-of-duties; platform admin alone cannot approve legal content.

## paragraph:293

Service-to-service OAuth/client credentials with least privilege and rotated secrets.

## paragraph:294

Webhook payload signed; replay window and delivery ID prevent replay.

## paragraph:295

Sensitive fields never exposed via generic UI projection without explicit projection policy.
