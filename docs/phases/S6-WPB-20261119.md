## OCR approach and provider decision

`CertificateExtraction:Provider` = `ExternalHttp` (default, pre-existing) or `LocalTextLayer` (new).
LocalTextLayer is an in-process, dependency-free reader of the embedded text layer of digital PDFs
(Flate, object streams, ToUnicode CMaps, TJ kerning, cm/Tm transforms) plus deterministic label rules.
No new package, no network, no secret: the policy rejects a local provider that carries an endpoint,
host or secret reference, and requires ModelVersion/PromptVersion to equal the actual engine/rule-set
versions. Basis: docs/dependency-policy.md (no unreviewed dependency) and docs/security-baseline.md
(no unapproved processor, no document content in logs/audit). **Image OCR (PNG/JPEG, scanned PDFs,
Identity-H without ToUnicode, encrypted PDFs) is an explicit UNAVAILABLE capability**, never an empty
success. Neither provider is enabled by default; enabling requires the full privacy/retention/processing
references and per-tenant/actor/vessel scopes already required by policy.

Confidence values are fixed rule scores (0.92 same-line, 0.78 next-line, ≤0.85 normalised date,
0.50 unparsed date, 0.40 ambiguous), **not calibrated probabilities**.

## Follow-up 19.11.2026 — vessel_reference matching (S6 gate QA finding)

Finding: `Project` compared `vessel_reference` with the vessel GUID string, so it was always
`SCOPED_REFERENCE_UNMATCHED`. Fix: `CertificateVesselMatch` (`backend/Poseidon.Domain/CertificateExtraction.cs`)
matches the extracted value against the scoped vessel's server-owned identifiers — `Vessel.Name`,
`Vessel.Code` and, if present, the user-declared `Known` IMO in the regulatory draft (unverified provenance) —
after normalisation (case, diacritics incl. Turkish dotted/dotless I, punctuation/whitespace, leading
MV/MT/MS/M/V/TUG prefix). Only exact normalised equality matches; partial names, wrong IMO digits and
missing scope stay `SCOPED_REFERENCE_UNMATCHED`. A match adds `SCOPED_REFERENCE_MATCH_SUGGESTED` +
`SCOPED_REFERENCE_MATCHED_BY_{NAME|CODE|IMO}`; the candidate stays `REVIEW_REQUIRED` and the human
vessel-context confirmation is unchanged. Identifiers are read through the actor's vessel scope and
tenant filter in `CertificateExtractionEndpoints.VesselIdentifiers` and never logged or returned.
`person_reference` was fixed in the second follow-up below.

Golden set now 20 documents (+`vessel-name-variant`, +`foreign-vessel`) with fictional per-document vessel
profiles and expected match kind. Re-run (actual): precision 1.000 (58/58), recall 0.841 (58/69), field
exact-match 0.921, document exact-match 0.800 (16/20), critical unsupported 0, authority bypass 0;
vessel match 8/8 expected matches, 0 false matches (foreign vessel and no-vessel documents unmatched).
Per-field recall: certificate_no 0.84, expiry_date 0.73, vessel_reference 0.69, others 1.00.
Thresholds re-pinned to this baseline (recall 0.84, exact-match 0.80, vessel match recall 1.00, false matches 0).

## Follow-up 2, 19.11.2026: person_reference matching

`person_reference` had the same GUID comparison. `CertificatePersonMatch` now compares the extracted value with the
bound person's crew identity, meaning the full name and the employee/seafarer number. These values are opened only
when `CrewIdentityPolicy.Allows(actor, read)` holds, the person belongs to the actor's tenant and the identity is
stored `ProtectedV1` and decrypts. The read sits in `CertificateExtractionEndpoints.PersonIdentifiers` and runs
after the existing crew file privacy gates. If any of these checks fails, no identifiers are used and the field
stays `SCOPED_REFERENCE_UNMATCHED`.

The normalisation is the same as for vessels, without stripping a ship-type prefix. A name needs at least two
tokens, and an employee number at least 3 characters. Only exact equality produces a match, which adds
`SCOPED_REFERENCE_MATCH_SUGGESTED` and `SCOPED_REFERENCE_MATCHED_BY_{NAME|EMPLOYEE_NO}`. The candidate stays
`REVIEW_REQUIRED` and the crew confirmation workflow is unchanged (still unavailable). Identity values are never
logged, audited or returned.
