Row 29 says "state" but does not list values. The lifecycle comes from 62.01 §6, not from an invented `draft/active/suspended` set. APPROVED means technical implementation approval only (62.01 paragraph:185). It is not legal or plan approval, completion, verification or effectiveness, and the API always returns `effectiveness: UNKNOWN`. The 62.01 dual-pointer model, in which a published revision stays current while its replacement is reviewed, is **not** implemented. Here any new content, submit or complete revision of an IN_REVIEW, APPROVED or PUBLISHED control returns it to DRAFT through an audited `CONTENT_REVISED` event. That is the conservative "prior approval is not current" reading, and it is a known gap.

## Freshness limit (explicit)

The 54.01 freshness policy registry does not exist. Stale and expired remain **declared** overlays (`DECLARED_STALE` and `DECLARED_EXPIRED` from the evidence's own `freshUntil`/`validUntil`). No freshness policy, maximum age or catalog was invented. Evidence with no declaration stays `UNKNOWN`, never fresh or current. VERIFIED validity is still bounded only by the declared dates, the qualified-source `MaxAgeHours` and the appointment validity.

## Risks

- The `CONTENT_REVISED` reset replaces the 62.01 "published stays current until replacement publish" pointer. Retiring after a reset requires a new review chain.
- Approval needs the full qualified-source chain. Without it, approve fails closed with `qualified_source_required` (by design). `control.approve` is a new server permission that operators must provision. No production role catalog exists.
- The orphan report deserializes candidate control content in memory per vessel. It is unbounded per vessel and will need paging or indexing at scale.
- The migration backfill runs `UPDATE` in a migration (not through audited SaveChanges). It only sets the honest initial DRAFT state on pre-existing control heads.
