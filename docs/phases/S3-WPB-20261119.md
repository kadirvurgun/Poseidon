Row 29 says "state" but does not list values. The lifecycle comes from 62.01 §6, not from an invented `draft/active/suspended` set. APPROVED means technical implementation approval only (62.01 paragraph:184). It is not legal or plan approval, completion, verification or effectiveness, and the API always returns `effectiveness: UNKNOWN`.

**Dual pointer (follow-up fix).** The source confirms the reading: a published revision stays the current one until its replacement is published (paragraph:188-190, 198, 447). The head now carries two things. `ControlState` is the state of the candidate (latest) revision. `PublishedRevision` is the effective published revision. Editing a PUBLISHED, APPROVED or IN_REVIEW control appends a successor revision and records an audited `CONTENT_REVISED` event that puts the candidate back to DRAFT ("prior approval is not current"). `PublishedRevision` is not touched, so the published revision stays effective. The successor's SUBMIT, RETURN and APPROVE never move it. Only the successor's PUBLISH moves the pointer. That event records `SupersedesRevision` (the previous published revision), and the head audit records the before/after of `PublishedRevision`. For an APPROVED control that was never published there is no effective revision: the edit returns it to DRAFT and `publishedRevision` stays null. RETIRE names the effective published revision (62.01 expectedCurrentRevisionId), is allowed while a successor is pending, clears the pointer (paragraph:193) and is terminal. The source and this implementation do not conflict.

## Freshness limit (explicit)

The 54.01 freshness policy registry does not exist. Stale and expired remain **declared** overlays (`DECLARED_STALE` and `DECLARED_EXPIRED` from the evidence's own `freshUntil`/`validUntil`). No freshness policy, maximum age or catalog was invented. Evidence with no declaration stays `UNKNOWN`, never fresh or current. VERIFIED validity is still bounded only by the declared dates, the qualified-source `MaxAgeHours` and the appointment validity.

The product rule is the correct source behaviour (the submit freezes the typed criterion set, 62.01 paragraph:177), so **the test was fixed and the product was not**. The successor now changes only the non-policy `Title` (`ControlLifecycleTests.cs:215`).

**QA B2 (retirement false green).** RETIRE nulls the pointer, so every `(PublishedRevision ?? Retirement is now modelled explicitly by the stored RETIRED state and the append-only RETIRE event. It is never inferred from a null pointer, because a never-published control also has a null pointer.

## Risks

- The successor model was authored against the 62.01 dual pointer. Its end-to-end behavior is covered only by the DEFERRED Integration tests. The list endpoint (`GET /controls`) remains the authoring view: its rows are the latest candidate revision. Its `lifecycle[]` entries (gate fix) show the 62.01 state and the effective published revision.
- 62.01 V1 publish fences (expectedContentHash, NOT_YET_EFFECTIVE, source fence) and the "Future draft" FORECAST row (paragraph:186-187, 194-196) are not implemented; publish uses the head xmin plus the exact candidate revision CAS.
- Approval needs the full qualified-source chain. Without it, approve fails closed with `qualified_source_required` (by design). `control.approve` is a new server permission that operators must provision. No production role catalog exists.
- The orphan report deserializes candidate control content in memory per vessel. It is unbounded per vessel and will need paging or indexing at scale.
- The migration no longer rewrites data. The former raw `UPDATE … SET "ControlState" = 'DRAFT'` was removed. A NULL state on a control means that no lifecycle event exists and is derived as DRAFT on read (domain, API, audit and context guard). So no business state changes outside the audited SaveChanges path, and no equivalent audit is needed.
