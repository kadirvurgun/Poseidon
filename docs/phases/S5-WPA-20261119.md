## Override authority decision (DEV-040) — source-defined, activation closed

Source: `60.03_POSEIDON_Mevzuat_Kaynak_ve_Uygulanabilirlik_Yasam_Dongusu_Tam_Analiz_TR_Rev4`
paragraph:154–166 (OverrideDecision, forbidden AI/admin/self approval, OVERRIDE_OVERLAP), 564
(`override.author/approve/revoke` IAM permissions), 575–576 (OVERRIDE_AUTHORITY policy: allowed actions,
max duration/review interval, required expertise, independent approver, **current AuthorityGrant required;
policy does not create a grant**), 580 (**no policy → activation closed**), REG-033..035 (paragraph:1075–1082).

Implemented exactly that: permissions `applicability.override.author|approve|revoke` (no default role or
configuration grants them); human actor only; author ≠ approver (maker-checker); approval also requires a
server-resolved AuthorityGrant from a published OVERRIDE_AUTHORITY policy. No such policy/grant store exists
in the repository, so `ApplicabilityOverrideEndpoints.AuthorityGrant` returns none and every approval is
**422 `override_authority_unavailable`**; no override can become ACTIVE (DB check also requires approver ≠
author and a grant id for ACTIVE). **Open expert decision:** who holds the grant (Regulatory Approver with
MARITIME_LEGAL expertise etc., 60.03 paragraph:584) and the published OVERRIDE_AUTHORITY policy content must
be supplied by the operator/expert; the UI says "An override requires a configured authority".

Mechanism: `ApplicabilityOverride` (+ append-only `ApplicabilityOverrideEvent`, `ComplianceCommandReceipt`,
DB triggers), controlled reason catalog per action, mandatory `reviewAt ≤ expiresAt`, ≤ 365-day technical
bound (no default), ACCEPT_INTERPRETATION only for authoritative APPLICABLE/NOT_APPLICABLE with a cited
evidence record. Read-time validity: changed evaluation/input hash/rule-set/rule revision or non-current
review → `REQUIRES_REVIEW`; `now ≥ min(reviewAt, expiresAt)` → `EXPIRED`. Optional admin fixture seeds only
a withdrawn (REVOKED) FICTIONAL proposal; no approval, grant or receipt.
