## Delivered behavior

- `POST /api/v1/renewal-workflow/{id}/transitions?vesselId=` (`CertificateRenewalTransition`): Serializable transaction, body `expectedVersion`+`expectedRevision`, idempotency receipt `RenewalTransition`, antiforgery, current-response fence. Each transition appends one immutable `RenewalRevisions` row with `State`, `Transition`, `DecisionJson`.
- VERIFY requires `certificate.renewal.verify`, COMPLETE requires `certificate.renewal.complete`; both Human-only (`human_actor_required`). Five MATCH checks are required; UNKNOWN is not a match. Nothing is derived from upload/OCR.
- COMPLETE writes immutable `assurance.CertificateSupersessions` (PK tenant+original, unique replacement, FK to exact revisions, immutability triggers). The original certificate revisions are untouched; reads mark them `SUPERSEDED`, `canEdit=false`; further certificate/renewal writes on it return `certificate_already_superseded`.
- Verified/Completed never claim legal validity: `qualification` stays `REVIEW_REQUIRED`, `SOURCE_QUALIFICATION_REQUIRED` stays.
- UI: `CertificateRenewalWorkflowPanel` (server-allowed steps only, loading/offline/stale/conflict/unknown-outcome with same-key retry), state badges in history/list; 56 keys × 17 locales.
- Contracts: endpoint profile, S1 critical op (158/149/159), 15 security result codes, closed audit projections (decision withheld), client vocabulary, permissions in `TrustedPermissions`/audit capabilities, host-exported OpenAPI + `api.d.ts`, migration `20261119165626_S6WpaRenewalWorkflow`.
