## Behaviour

- **DEV-089**: one execution per job and tug (`ACTIVE|SUSPENDED|COMPLETED|ABORTED`, verification `PENDING|VERIFIED|REJECTED`). Start
  requires the current approved DEV-087 plan covering the tug, the issued DEV-088 briefing with every participant ACK, an active DEV-083
  assignment and the latest DEV-084 GO human record for the current assignment revision whose assessment hash still equals the current
  readiness assessment; it never creates a GO. Start/suspend/resume/abort/complete need a server-provisioned Tug Master/Master
  appointment on the executing tug (shore, AI and system identities hold none). Abort is accepted in ACTIVE and SUSPENDED without a
  version precondition. Resume re-checks the pinned plan and briefing; complete needs an end position, a 20..4000 note and a released
  towline. The timeline is an append-only, SHA-256 hash-chained ledger (towline connected/released, tow load value + unit `t|kN`,
  communication GOOD/ATTENTION/LOST, recorded weather values, winch state, emergency release test, position, evidence references,
  notes); observed instants are never in the future (2 min device clock tolerance) or before the start. A terminal execution accepts
  only evidence and notes. Verification is a separate person (`tug.execution.verify`, Human), never the starter or finisher (DB CHECK).
- **DEV-090**: one log per tug/date/watch (`00-08|08-16|16-24|OTHER`), client-generated id, Idempotency-Key receipts and ExpectedVersion
  (offline replay is idempotent; a changed base is a material 409). Content: IANA time zone, engine runtime meters (opening/closing,
  reset evidence), fuel (quantity + unit `L|m3|t` + source), links to the tug's towage executions and defects, daily summary.
  A closing reading below the opening without reset evidence is `meter_sequence_conflict` (409). Reconciliation (advisory):
  meter continuity against the previous log of the same meter (gap/regression/unknown previous → REVIEW_REQUIRED), executions of the
  log interval not linked or linked outside it, jobs completed and ACTIVE-interval operating hours. Safety events stay
  `UNKNOWN:SafetyEventSourceUnavailable` (WP-B owner not available). Master VERIFY/RETURN is a Tug Master/Master human record bound
  to the content hash; never an author or the submitter. The UI keeps one unsaved command in memory while offline and replays it with its
  original key (sync state SYNCED/LOCAL_PENDING/CONFLICT/FAILED); durable on-device capture stays unregistered per 60.02 p284.
- **DEV-111**: drydock package (`DRAFT→PLANNED→IN_PROGRESS→COMPLETED→VERIFIED`, `CANCELLED`) with project, yard, planned dates,
  scope items (structural category, equipment, work package, class/statutory requirement, priority) and links pinned to an exact
  revision of work orders, defects, certificates and pre-survey checklists, each read through its owner's read gate. Readiness shows
  unlinked, overdue (WO due date, certificate expiry/survey window passed), STALE (target revision changed since pinned) and UNAVAILABLE
  links; it is linkage completeness only, never a survey result. Cost/currency/vendor/budget are external reference values only.
  Complete requires evidence references; verification is a different person (`drydock.verify`, Human; DB CHECK).
