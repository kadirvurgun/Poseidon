## Delivered behaviour
DEV-069 closure
- Every committed import row writes one insert-only `integration.ImportProvenance` row (tenant, vessel, batch, preview, row number, source hash, template version + fingerprint, target kind/id, target revision — `RowVersion` for Vessel — CREATE/UPDATE, actor, time) inside the same SERIALIZABLE, audited commit transaction. No source cell values.
- `GET /api/v1/vessels/{vessel}/imports/{batch}/provenance?offset&limit` (limit ≤ 100), readable by any import reader with the batch category's read rights (not session-bound).
- Commit still runs each category's ordinary owning handler; a source guard test forbids `ExecuteUpdate/ExecuteDelete/FromSql/ExecuteSql/IgnoreQueryFilters/SqlQuery` and direct entity inserts in the import paths; an integration test proves an out-of-catalog criticality is rejected at preview and commit with no provenance.
- `ImportTemplates.Versions` is the single category → version list; the reconciliation screen lists it.

DEV-070
- `integration.ReconciliationReports`: explicit pinned batch set (1..50), immutable snapshot of counts (source = accepted + rejected + not committed, duplicates ⊆ rejected; DB CHECK), missing-critical list, deterministic sample (recorded seed, SHA-256 order, size 1..100 chosen by the author) and snapshot hash. Only lifecycle columns change (guard). One current report per vessel (filtered unique index).
- Critical field set `DEV-070-critical-fields-v1` via `RequiredDataPolicy` (vessel code/name; crew position/from; certificate type/issuer/issue/expiry/evidence; equipment code/name/level/criticality). Blank = MISSING, explicit UNKNOWN = UNKNOWN; both listed. A listing rule, not an approved catalog: the data owner confirms or records exceptions.
- `integration.ReconciliationSignOffs`: insert-only human record — decision `ACCEPTED | ACCEPTED_WITH_EXCEPTIONS | REJECTED`, reason ≥ 10, exceptions (kind/reference/disposition), sample-verified ids, appointment id + hash. `ACCEPTED` is refused while any open item exists; `ACCEPTED_WITH_EXCEPTIONS` must disposition every open item.
- Authority: `import.reconciliation.sign` permission plus an exact current `DataOwnerAuthorities` membership appointment (vessel, role context, period, source), exactly one Human membership. Membership administrators, tenant-wide managers without appointment, AI/automation/service principals, the report author and any uploader of a pinned batch cannot sign (DB CHECK: signer ≠ author).
- A newer committed import or a newer report makes the report `SUPERSEDED`; its sign-off becomes `INVALIDATED_SUPERSEDED` without editing the human record. A pinned batch that moved after the snapshot makes the report stale and refuses sign-off (409 `reconciliation_stale`).
- Endpoints: `GET/POST /api/v1/vessels/{vessel}/reconciliation-reports`, `GET .../{id}`, `POST .../{id}/sign-off` — CSRF, Idempotency-Key receipts (`ImportReconciliationReceipts`), strict JSON, SERIALIZABLE via `PostgresFailure`, xmin + hash concurrency.
- UI `/app/data-reconciliation/{vessel}` (`DataReconciliationWorkspace.tsx`): template versions, report list, create form, counts, pins, missing list, sample checkboxes, open items, blockers, sign-off form; unsigned = "Onay bekliyor"/"Awaiting sign-off" (warning tone), never green; loading/empty/error/offline/conflict/stale/forbidden states; 17 locales.
